# Head-pose geometry work

- Use `.venv/bin/python -m pytest` for tests and `.venv/bin/python` for repository tools.
- Keep pose, geometry, fusion, and teacher components independently configurable; disabled means the existing model path and checkpoint contract stay unchanged.
- Do not commit checkpoints, generated pseudo-labels, derived caches, or datasets.
- Preserve the fixed source-video train/val/test split. Generate training supervision from train records only, and require predicted HEAD detections for deployment-style validation/test.
- Record coordinate conventions, cache provenance, seeds, checkpoint hashes, and validation-selected thresholds for every experiment. Never select settings on test results.
- Treat W&B as the durable store for training conditions and metric history, but do not assume checkpoint artifacts were uploaded. Production trainers must update local `last` every epoch and `best` on validation improvement. Periodic `epoch_NNN` recovery snapshots must be at least five epochs apart, rotate to at most the newest one while training, and be removed after successful completion so only `last` and `best` remain. Successful small-scale and overfit gates must keep only one best checkpoint per model/checkpoint directory and remove successful `.previous_*` attempts; a failed retry may keep only its immediately preceding attempt. Do not add an unbounded checkpoint history without an explicit user request and a documented storage budget.

## Common performance evaluation

- Every enabled architecture scheduled in `configs/training_queues/*.yaml` must be evaluated with the same baseline-aligned contract below. Write both validation and test artifacts under the architecture output as `evaluation/{val,test}/baseline_aligned/{metrics.json,comparison_table.md,success.json}`. A metric that the architecture cannot produce must remain in the common table as `null`/`N/A` with an `unsupported_reason`; never remove the row.
- Use only the fixed group-preserving Face DINO V3 annotations in `outputs/dataset_cache/face_pose_drive_v2_balanced_811/annotations/face_dino_v1/{train,val,test}.json`: train = 44 groups / 4,237 images / 7,129 Heads, validation = 6 / 530 / 882, and test = 6 / 528 / 806. Verify the annotation SHA-256 recorded in each result before comparison. Do not substitute another split with the same image count.
- Use the locked deployment operating points unless a report explicitly labels an additional validation-selected operating point: Head score `0.30`, at most 100 Head detections per image and no NMS; Head ROI is a square of side `1.20 * max(Head width, Head height)`; Face/ellipse score `0.80`; keypoint presence score `0.70`; Head-to-GT matching IoU `0.50`. Lock any alternative threshold on validation and then apply it unchanged to test.
- Normalize keypoint error by `1.20 * max(GT Head width, GT Head height)`. Report NME thresholds `0.05` and `0.10` with fixed semantic slots `left_eye`, `right_eye`, `nose`, `left_mouth`, and `right_mouth`; aggregate semantic groups as eye = slots 0–1, nose = slot 2, mouth = slots 3–4. Keypoint states are missing = 0, occluded = 1, visible = 2. Exclude ambiguous/invalid Head annotations from attribute metrics and report their count.
- Report the full common table: (1) Head COCO bbox AP, AP50, AP75, AP small/medium/large, AR@1/10/100, and AR small/medium/large; (2) Face-presence macro F1, face-present recall, no-face recall, false-face rate, and TP/FP/FN/TN; (3) ellipse mean/median/P10 IoU, fractions at IoU 0.50/0.75, center NME, major/minor radius relative error, and angle MAE for GT axis ratio at least 1.05; (4) keypoint semantic macro F1 and micro recall at NME 0.05/0.10, matched/visible/occluded NME at 0.10, plus eye/nose/mouth prediction count, GT count, precision, recall, and F1; (5) state accuracy, state macro F1, visible F1, conditional occluded F1, occluded end-to-end precision/recall/F1, and the occluded/visible confusion matrix; (6) the Face, ellipse, keypoint, and state metrics again after predicted Heads are matched to GT Heads; (7) hard-case slices for all-five-visible, one-to-four-visible, all-missing, occluded, high/low eccentricity, image-edge, and smallest-Head tercile; and (8) end-to-end elapsed time, images/second, model inference milliseconds/image, peak VRAM, batch size, and input size.
- Attribute metrics anchored on GT Heads are diagnostic and must be labeled separately from deployment-style metrics anchored on predicted Heads. Test comparison tables must use the locked validation contract and include absolute and relative deltas from the designated baseline report; test results must never choose a threshold, checkpoint, architecture, or other setting.
- Record in `metrics.json`: schema version, architecture ID, stage/branch used for comparison, checkpoint path and SHA-256, config path and SHA-256, git revision and dirty state, annotation paths and SHA-256, coordinate and ellipse-IoU conventions, cache paths and provenance, random seeds, thresholds and their selection source, image/Head/valid/ignored counts, and unsupported reasons. Write `success.json` only after the expected split inventory and every supported metric assertion pass.

## Training queue gates

- Add every new architecture to `configs/training_queues/pending_models_tests_then_training.yaml`; the older queue files are execution history, not extension points. The canonical queue must keep all enabled gate jobs before every incomplete `production_train` job.
- Every incomplete production architecture requires four explicit success-marker dependencies: `schema`, `gpu_step`, `overfit`, and `small_scale`. The small-scale gate must use the production model/loss/AMP path on a bounded real train/validation subset and must verify a finite, improving validation metric before production training can start.
- Keep the canonical order as all architecture gate groups, then one contiguous production-training group, then evaluation/post-processing. This ordering is intentional: finish failure-prone checks while the operator is present and reserve unattended time for continuous full training.

- Treat each architecture's real-data overfit/preflight test and production training as one dependency group in `configs/training_queues/*.yaml`.
- Production training must explicitly depend on a successful test gate. If that gate exits with an error or does not produce its dedicated success marker, skip the production job for that architecture; independent architecture groups may continue.
- Keep diagnostic reports separate from success markers. Files such as `overfit_report.json` may be written on failure and must never be used alone as proof that a gate passed. Write and use a dedicated success marker only after every required assertion succeeds.
- On queue restart, never infer success from a diagnostic report or stale status. Resolve dependencies from explicit success markers and record dependency skips in `outputs/training_queues/*/status.json`.
