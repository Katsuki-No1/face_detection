## Face-contour versus internal occlusion (user-defined 2026-10-09)

- Interpret source FACE `occluded=false` as a visible face contour with sufficient information for face detection; `occluded=true` indicates occlusion also affects the face contour. This is the dataset annotation meaning supplied by the user, not a guarantee that a model detects the face.
- Keypoint `state=1` indicates annotated internal facial occlusion. Keep contour occlusion and internal keypoint occlusion as independent axes. `face_occluded=false` together with occluded keypoints is an expected meaningful class, not an annotation inconsistency.

- Cross these descriptors with the adopted profile-ratio slices and image truncation independently. Keep GT slice labels fixed when comparing models, with explicit denominators and counts. Do not filter GT slices using predicted keypoint states.

- Use a hierarchical evaluation table: first split by GT `face_occluded=false/true`, then split each group by the exact number of GT keypoints with `state=1`: `0`, `1`, `2`, `3`, `4`, `5`. The occluded-keypoint count defines occlusion severity within each face-occlusion group. Keep all twelve condition rows explicit rather than collapsing counts into an unapproved light/medium/heavy scale.
- Missing keypoints (`state=0`) do not increase this severity count. Retain missing counts separately. A zero-occluded-keypoint row with missing points is not evidence of a completely unoccluded face. Preserve annotation-invalid/unassociated exclusions as N/A with their counts, rather than assigning them to zero severity.
- Determine and describe a model's occlusion strengths/weaknesses using the fixed validation split under these conditions. Test performance must not determine occlusion rankings, tune conditions, or select model settings. Any later test corroboration remains separately labeled.
- Whenever reporting model performance, include a dedicated validation occlusion-robustness table separately from the basic/overall performance table. Its structure is: face-occlusion group, occluded-keypoint count, eligible GT sample count, and the agreed performance metric columns. Empty cells/conditions must remain N/A with support counts, never interpreted as successful robustness.
- The hierarchy, severity definition, validation split, and separate-table reporting requirement are agreed specifications. The exact performance metric columns, per-metric denominators, and quantitative criteria for declaring a strength/weakness remain to be discussed; do not silently treat an assistant proposal as an accepted criterion. This agreement records reporting requirements and does not itself authorize evaluator implementation or execution.

## Overlapping-face keypoint misassociation (agreed scope 2026-10-09)

- When faces overlap, treat face-detection difficulty within the occlusion-performance category. Retain the agreed GT face-contour flag and occluded-keypoint counts; geometric overlap alone must not overwrite the source occlusion annotations.
- For keypoint performance, retain a separate overlapping-face evaluation condition: the central failure is a keypoint belonging to the target face being predicted at another face's keypoint (cross-face misassociation). Do not collapse this evaluation into the number of occluded keypoints or a general face-detection result.
- Separate cross-face misassociation from ordinary localization error and missing predictions when designing the report. Spatial proximity to another face alone does not establish misassociation; the eventual definition must account for the intended target face and competing faces.
- Agreed now: the evaluation purpose and distinction between face detection versus keypoint attribution. Still pending discussion: how to define an overlapping-face sample and overlap severity, exact attribution/error criteria (including semantic slots and ambiguous cases), metric denominators, and final report columns. Previous assistant-proposed IoU/NME/point-presence thresholds for this specific diagnostic are not independently approved by this scope agreement.
- This is a model-performance evaluation specification memo; no implementation, inference, or evaluation execution is requested by recording it.

## Training queue gates

- Add every new architecture to `configs/training_queues/pending_models_tests_then_training.yaml`; the older queue files are execution history, not extension points. The canonical queue must keep all enabled gate jobs before every incomplete `production_train` job.
- Every incomplete production architecture requires four explicit success-marker dependencies: `schema`, `gpu_step`, `overfit`, and `small_scale`. The small-scale gate must use the production model/loss/AMP path on a bounded real train/validation subset and must verify a finite, improving validation metric before production training can start.
- Keep the canonical order as priority active-learning inference/frame extraction, all architecture gate groups, one contiguous production-training group, then evaluation/post-processing. Data acquisition runs first; after that, finish failure-prone checks while the operator is present and reserve unattended time for continuous full training.

- Treat each architecture's real-data overfit/preflight test and production training as one dependency group in `configs/training_queues/*.yaml`.
- Production training must explicitly depend on a successful test gate. If that gate exits with an error or does not produce its dedicated success marker, skip the production job for that architecture; independent architecture groups may continue.
- Keep diagnostic reports separate from success markers. Files such as `overfit_report.json` may be written on failure and must never be used alone as proof that a gate passed. Write and use a dedicated success marker only after every required assertion succeeds.
- On queue restart, never infer success from a diagnostic report or stale status. Resolve dependencies from explicit success markers and record dependency skips in `outputs/training_queues/*/status.json`.
